# Effect Rows for Racklr: A Fully Revised Plan

**Status:** Revised draft for working-group review
**Scope:** Extending the UIR and pass pipeline with algebraic effect rows, targeting Python (FastAPI, Django), TypeScript, React, and htmx. Next.js is treated as one instance of the general web-framework pattern, not as the design center.

---

## 1. The Corrected Focus

Effects exist to make the **mutator interfacing** generated by web frameworks safe. In every target stack, there is a set of functions that change state or interact with the outside world:

- **FastAPI route handlers** — async functions decorated with `@app.get`, `@app.post`, etc.
- **Django views and form handlers** — functions that receive requests and mutate the database.
- **React event handlers** — `onClick`, `onSubmit`, `onChange` callbacks.
- **htmx-triggered endpoints** — server-side functions that respond to partial-page requests.
- **Client-side state setters** — `useState` setters, `useReducer` dispatchers.

These are the **mutators**. The contract problem is to ensure each mutator performs only the effects it is allowed to perform, within its budgets and scopes. Racklr's UIR currently captures the structure of these mutators — `uir-fn` for handlers, `uir-event` for event bindings, `uir-call` for invocations — but not their effect behavior. This plan adds that layer.

---

## 2. What Racklr Has Today

Racklr provides:

- ANTLR4 grammar-driven parsing to CST.
- CST → UIR lowering with 40+ node types across Tier 0 (computational) and Tier 1 (OOP/module).
- UIR → Python 3 and JavaScript emitters with working round-trips.
- A documented UIR schema covering Tier 0 nodes: `uir-fn`, `uir-call`, `uir-if`, `uir-try`, `uir-decorated`, etc.
- 1,129 passing tests.

Tier 2 (UI component trees) is described in the schema as "models declarative component trees" but is **not yet implemented** in the UIR schema doc. The roadmap lists React/JSX and Svelte as planned Tier 2 lowering and emit targets.

The relevant existing infrastructure for this plan is the `uir-fn`, `uir-call`, `uir-decorated`, and `uir-try` nodes, plus the `lower-python.rkt` and `lower-javascript.rkt` modules that already handle decorators, async functions, and class methods.

## 3. The Effect Row Model

An effect row is an ordered set of **effect entries** attached to a function or mutator node.

### 3.1 Entry structure

Each entry has:

| Field | Description | Example |
|---|---|---|
| `name` | Opaque symbol, never interpreted by racklr | `llm`, `db`, `network`, `state-mutation` |
| `modality` | `may`, `must`, or `must-not` | `may` |
| `ops` | Specific operations constrained (empty = all) | `(query)` |
| `budget` | Integer upper bound on invocations | `5` |
| `scope` | Information-flow or resource qualifier | `reads=search_index` |

### 3.2 Semantics

- **Absence is prohibition.** An effect not listed is `must-not` by default.
- **`may` is permission, not obligation.** A function typed `<may llm>` may or may not call the LLM.
- **`must` is obligation.** A function typed `<must llm>` must perform at least one LLM operation on every execution path.
- **Budgets are upper bounds** on operation invocations. Statically resolvable where the call graph is finite; otherwise lowered to runtime counters.
- **Scope is a constraint** on resources or information flow.

### 3.3 Contract algebra

The algebra operates on the canonicalized UIR form:

| Operator | Meaning |
|---|---|
| `A ∪ B` | Union of entries; budgets sum |
| `A ∩ B` | Intersection of entries; budgets take minimum |
| `A − B` | Set difference; used for capability revocation |
| `A ≤ B` | Subtype: every `may` in A is `may` in B; budgets in A ≤ budgets in B |

## 4. UIR Extensions

### 4.1 New node types

```
(struct uir-effect-row (entries) #:transparent)
(struct uir-effect-entry (name modality ops budget scope) #:transparent)
(struct uir-effect-op (effect op signature) #:transparent)
(struct uir-effect-handler (effect body handlers) #:transparent)
(struct uir-capability (effect scope) #:transparent)
(struct uir-subtype (left right) #:transparent)  ; first-class per working-group answer
```

### 4.2 Extended mutator nodes

```
(struct uir-fn   (name params ret body effects decorators) #:transparent)  ; extended
(struct uir-event (name handler effects) #:transparent)                    ; extended
(struct uir-state (name initial setter effects) #:transparent)             ; extended
```

The `effects` field is a `uir-effect-row` or `#f`. The `decorators` field on `uir-fn` is existing; effect annotations may be carried as a decorator.

## 5. Parsing Native Effect Annotations

Effects are written in the host language's native syntax. The parser for each language recognizes that syntax and produces `uir-effect-row` nodes.

### 5.1 Python

Three mechanisms, in priority order:

**Mechanism A: Decorator.** The most natural for FastAPI and Django:

```python
@effects(llm={"max": 5}, db={"reads": "search_index"})
async def summarize(input: str) -> str:
    ...
```

The `lower-python.rkt` parser already handles decorated functions; extending it to recognize `@effects(...)` and extract the row is a direct addition.

**Mechanism B: Type annotation via `Requires`-style brand.** A function can be annotated with a branded type that the parser recognizes:

```python
def summarize(input: str) -> str: ...  # with a __effects__ attribute
summarize.__effects__ = {"llm": {"max": 5}}
```

**Mechanism C: Inference.** If no annotation is present, the effect row is inferred from the body (see §6).

### 5.2 TypeScript / TSX

**Mechanism A: Decorator-like wrapper.** For React components and hooks:

```tsx
const summarize = withEffects({ llm: { max: 5 } })(
  async (input: string) => { ... }
);
```

The `uir-decorated` node already exists; the parser can recognize this pattern and attach the row to the inner `uir-fn`.

**Mechanism B: JSDoc tag.** For code that cannot be structurally modified:

```tsx
/**
 * @effects llm(max=5), db(reads=search_index)
 */
async function summarize(input: string): Promise<string> { ... }
```

The `lower-typescript` parser would need to be extended to recognize `@effects` tags. (TypeScript lowering is planned, not yet implemented; this is an addition to that planned module.)

**Mechanism C: Inference.** Default when no annotation is present.

### 5.3 htmx and Django

htmx-triggered endpoints are ordinary FastAPI or Django view functions; the same Python mechanisms apply. Django form handlers and view functions follow the same pattern. No separate parsing mechanism is needed.

## 6. Effect Inference

The inference pass (Pass 2.4) computes effect rows for mutators that lack annotations. Per the working-group's answer, effects are **inferred** by default.

The algorithm:

1. Walk the UIR, building the call graph.
2. Initialize each `uir-fn`'s effect row to `⊥` (empty, pure).
3. Iterate to fixpoint: a function's row is the union of its callees' rows plus any directly performed effects.
4. Direct effect detection rules:
   - `fetch` / `axios` calls → `network`
   - `db.*` / `Model.objects` calls → `db`
   - `llm.*` / `openai.*` calls → `llm`
   - `useState` setter calls → `state-mutation`
   - `revalidatePath` / cache invalidation → `cache`
5. For recursion, use a monotone worklist; rows converge because the effect set is finite.
6. For higher-order calls where the callee is unknown at compile time, **defer to runtime** (per working-group answer 10.2). The deferred effect is represented as `uir-effect-entry` with modality `unknown`.

The inference result is written back to `uir-fn.effects`. Downstream passes see a fully-populated row.

## 7. Contract Algebra Pass

Per the working-group's answers:

- **(10.3) First-class:** The `≤` relation is a `uir-subtype` node that survives lowering.
- **(10.5) Static first, runtime fallback:** The pass attempts static resolution of budgets and scopes. When it can prove a constraint, it emits a compile-time check. When it cannot, it emits a runtime guard.
- **(10.4) Jolt:** The shared validator is built in Jolt, called via C ABI.
- **(10.6) Fixture:** A shared fixture spec exercises all five structural features.

The pass checks three properties:

**Subtyping.** A mutator's inferred or annotated row must be a subtype of its component's allowed row. If a component declares `<may state-mutation>` and a mutator is inferred to use `<may network>`, the pass reports a compile-time error unless the component's row is widened.

**Budgets.** A mutator annotated `<may llm(max=5)>` must not statically call the LLM more than five times on any execution path. If the count is not statically resolvable, the pass emits a runtime guard.

**Prohibitions.** A mutator annotated `<must_not db>` must not call any function inferred to have the `db` effect.

Errors are reported in the same diagnostic channel as parse and lowering errors.

## 8. Runtime Enforcement via Jolt

For effects that cannot be statically resolved, the pass emits a runtime guard that calls the Jolt validator. The validator's interface:

```c
int validate_effects(const char* agent_type, const char* effects_json, char** error_msg);
```

### 8.1 Python emission (FastAPI / Django)

For a FastAPI route handler:

```python
@app.post("/profile")
@effects(db={"writes": "user"}, cache={"revalidates": "/profile"})
async def update_profile(data: ProfileData):
    __validate_effects("profile-mutator", ["db:writes=user", "cache:revalidates=/profile"])
    await db.user.update(where={"id": data.id}, data=data)
    revalidate_path("/profile")
```

The `__validate_effects` function is a thin wrapper that loads the Jolt shared library via `ctypes` or `cffi`. For Django views, the same wrapper is emitted inside the view function.

### 8.2 TypeScript / React emission

For a React event handler:

```tsx
<button onClick={__withEffects("counter-mutator", ["state-mutation:component=counter"], () => setCount(count + 1))}>
  Click
</button>
```

The `__withEffects` wrapper performs the same validation before invoking the handler. For htmx-triggered endpoints, the server-side Python guard applies.

### 8.3 Validator deployment

The Jolt validator is compiled once to a shared library (`.so`/`.dylib`/`.dll`) and called from:

- **Python:** `ctypes` / `cffi`
- **TypeScript/Node.js:** `ffi-napi` / `koffi`
- **Rust:** `extern "C"` link
- **Clojure/Jolt:** direct call

The same binary enforces the same contract everywhere.

## 9. Revised Pipeline

```
Pass 1:    Parse (per-language ANTLR grammar, extended for effect annotations)
Pass 1.5:  Effect Annotation Extraction (parser → uir-effect-row)
Pass 2:    CST → UIR (existing, extended to attach effect rows to uir-fn/uir-event/uir-state)
Pass 2.4:  Effect Inference (fixpoint on call graph; defer higher-order to runtime)
Pass 2.5:  Contract Algebra (subtyping, budgets, prohibitions; emits uir-subtype nodes)
Pass 2.6:  Runtime Fallback Emission (uir-effect-handler → Jolt validator calls)
Pass 3:    Target Lowering (existing, extended to know effect rows)
Pass 4:    Emission (existing, extended to emit guards or brands)
```

Pass 1.5 is parser-side. Passes 2.4, 2.5, and 2.6 are language-agnostic.

## 10. Target Mapping

| Target | Parse (front-end) | Emit (back-end) |
|---|---|---|
| **Python (FastAPI)** | Decorator `@effects(...)` or `__effects__` attribute | `@effects(...)` + `__validate_effects(...)` guard |
| **Python (Django)** | Same | Same, inside view function |
| **TypeScript (React)** | `withEffects(...)` wrapper or JSDoc `@effects` | `__withEffects(...)` guard or branded type |
| **htmx** | Same as Python (server-side endpoints) | Same as Python |
| **JavaScript** | `withEffects(...)` wrapper | `__withEffects(...)` guard |

The algebra and inference passes remain language-agnostic.

**Phase 1 — UIR and Python annotation extraction (4 weeks).**
Extend `uir-fn`, `uir-event`, and `uir-state` with `effects` fields. Extend `lower-python.rkt` to recognize `@effects(...)` decorators and `__effects__` attributes. Write fixture tests for a FastAPI route handler and a Django view.

**Phase 2 — Effect inference and contract algebra (4 weeks).**
Implement Pass 2.4 (fixpoint inference) and Pass 2.5 (subtyping, budgets, prohibitions) on the UIR. Test against a FastAPI + SQLAlchemy fixture and a Django ORM fixture.

**Phase 3 — Runtime fallback and Jolt validator (4 weeks).**
Implement Pass 2.6. Build the Jolt validator shared library with the C ABI. Wire `__validate_effects` emission into the Python emitter.

**Phase 4 — TypeScript / React support (6 weeks).**
Implement the TypeScript parser and lowering (currently planned, not implemented). Extend it to recognize `withEffects(...)` and JSDoc `@effects`. Implement effect inference for React hooks and event handlers. Wire `__withEffects` emission.

**Phase 5 — Cross-language consistency testing (4 weeks).**
Build the fixture spec (§12). Emit it to Python (FastAPI), TypeScript (React), and JavaScript. Verify that all three enforce the same contract via the Jolt validator.

**Phase 6 — htmx and Django integration testing (3 weeks).**
Test the Python emitter against htmx-triggered FastAPI endpoints and Django form handlers. Verify that server-side mutators are guarded identically to React handlers.

## 12. Fixture Specification

The fixture exercises all five structural features. It is written in each target language's native syntax and must round-trip through the UIR.

**Python (FastAPI) source:**

```python
from myapp.effects import effects, llm, db, network

@effects(llm={"max": 5})
async def summarize(input: str) -> str:
    return await llm.query(f"Summarize: {input}")

@effects(llm={"max": 10}, db={"reads": "search_index"})
async def researcher(query: str) -> Report:
    rows = await db.fetch("search_index", query)
    return await llm.query(f"Analyze: {rows}")

@effects(must_not={"network"})
def forbidden(x: str) -> str:
    return x

@effects(llm={"max": 15}, db={"reads": "search_index"})
async def pipeline(seed: str) -> Report:
    report = await researcher(seed)
    summary = await summarize(report.summary)
    return Report(report.rows, summary)
```

**Expected UIR (abridged):**

```
(uir-fn "pipeline"
  ...
  (uir-effect-row
    (list (uir-effect-entry "llm" "may" '() 15 #f)
          (uir-effect-entry "db"  "may" '() #f "reads=search_index"))))
```

The fixture is emitted to all target languages. Each target's test verifies:

1. Budget enforcement (call count exceeds `max` → violation).
2. Prohibition enforcement (`must_not` effect invoked → violation).
3. Obligation enforcement (`must` effect not invoked → violation).
4. Scope enforcement (`db(reads=search_index)` invoked on wrong table → violation).
5. Subtyping (`summarize` callable where `researcher` is expected, but not vice versa).

## 13. Open Questions

1. **JSDoc vs. wrapper for TypeScript.** JSDoc is less invasive but not checked by TypeScript. `withEffects(...)` changes the function signature. Should the parser support both?
2. **Django middleware vs. view decorators.** Should effects be extracted from view decorators only, or also from middleware that wraps handlers?
3. **Client-side state mutation granularity.** Should `state-mutation` be tracked at the component level, the hook level, or the setter level?
4. **Runtime guard overhead.** `__withEffects` adds a function call per event invocation. Should the emitter support a sampled validation mode for high-frequency events?
5. **Cross-language consistency.** The Jolt validator is the single source of truth for runtime enforcement, but static inference in racklr and runtime tracking in the target language's effect library may diverge. How is this divergence detected?
